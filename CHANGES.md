# Changelog

## v2.9.1 (2026081200)

Bug fix release. Penalties recorded in the grader did not always reach the gradebook. **Some existing grades are wrong and are not corrected automatically** — see *What to check* below.

### What went wrong, in plain terms

When a marker records a penalty in the Unified Grader — a word-count deduction, or the outcome of an academic integrity review — the grader immediately shows the reduced mark, and has always done so correctly. What did not always happen was the second step: writing that reduced mark into the gradebook.

The deduction only reached the gradebook when the grade was saved *after* the penalty was recorded. That made the fault look intermittent rather than systematic, and it is why it went unnoticed for so long:

- **Penalty applied while marking** — the marker adds the penalty and then saves the grade moments later. The grade save carried the deduction through, so these are correct.
- **Penalty applied after the grade was already issued** — typically an academic integrity outcome decided weeks later. Nothing saves the grade again afterwards, so nothing recalculated. The penalty was stored, the grader displayed it, and the gradebook quietly kept the original mark.

Two related faults had the same shape. **Removing** a penalty never restored the mark, so a deduction lifted after appeal stayed in place. And on **quizzes** a penalty never applied at all, in either order, because a quiz mark is produced by the question engine rather than typed by a marker and the deduction was never carried across to it.

Late penalties were unaffected throughout. Where a late penalty and a manual penalty both apply they now accumulate correctly, on assignments, forums and quizzes alike.

### What to check

Students whose penalty was applied **after** their grade was issued are the affected group, most likely those coming out of an integrity process. Their gradebook mark will be higher than the figure the grader displays.

Re-saving the grade through the Unified Grader corrects it, because the save now recalculates. Comparing the grader's "final grade after penalties" against the gradebook column will show whether a given student is affected.

### Fixes

- **A penalty applied after the grade was issued never reached the gradebook.** `save_penalty` and `delete_penalty` wrote their row and returned without syncing. Every other path that changes a grade calls `sync_gradebook_penalty()` — `save_grade`, `clear_all_overrides`, `delete_forum_extension`, `forum_extension`, `overrides_extensions` — but the two penalty endpoints did not, so the deduction only reached the gradebook if something else happened to save the grade afterwards. Both endpoints now sync. The sync recomputes from the activity's raw mark and the current penalty rows on every call rather than adjusting the previously synced value, so calling it from the penalty path as well as the grade path cannot deduct twice.
- **Removing a student's last penalty left the reduced mark in the gradebook permanently.** `assign_adapter::sync_gradebook_penalty()` returned early when the total deduction was zero, so no path ever wrote the restored figure back. Found by the regression test for the fix above, which passed on adding a penalty and failed on removing one. `forum_adapter` was already correct here.
- **Manual penalties never applied to quizzes.** A quiz mark is computed by the question engine, so `quiz_adapter` inherited a no-op sync and a word-count or integrity penalty reached no grade at all while the grader displayed it as though it had. It now pushes the penalised figure through `quiz_grade_item_update()`, which raises `user_graded` — the event a late-penalty access rule observes — so that rule re-applies its own deduction on top and the two compound, without this plugin needing to know how the late penalty is calculated. The same division of labour assignments already rely on. Because a late-penalty rule pins the gradebook cell with an override to stop the quiz module overwriting it, the sync lifts the override, writes, and makes sure the cell is pinned again before returning; leaving it unpinned would let the next recalculation restore the un-penalised mark. A locked grade is left untouched.
- **Typing `-` to clear an assignment grade did not persist.** The field went blank and the previous mark returned on the next page load. `assign::apply_grade_to_user()` guards its write with `isset($formdata->grade)`, and `isset()` is false for null, so the clear was silently dropped. Null grades now take the direct save path, which stores mod_assign's own `-1` sentinel. `forum_adapter` has always done this; assign never got the same guard.

### Test infrastructure

- **The Behat suite had never run, and reported success on every build.** `tests/behat/behat_local_unifiedgrader.php` opened with `defined('MOODLE_INTERNAL') || die();`. Behat loads context classes while building its suite list, before `config.php`, so `MOODLE_INTERNAL` was undefined and the guard fired; a bare `die()` exits with status **0** and prints nothing, so the runner saw a clean exit. One bad context file takes the whole run down, so all eight feature files were affected. Core's own context classes carry an explanatory comment in place of this guard for exactly this reason.
- With the process alive, three further defects surfaced in sequence, each hidden by the previous one: the context called `unescape_argument()`, which does not exist on `behat_base` in Moodle 5.0 and whose absence aborted every scenario in its Background; seven assertions passed a CSS selector to core's `the field "X" matches value "Y"`, which resolves X by label, name, id or placeholder only, and the grade input has none of those; and the step that types a grade returned without waiting for the autosave it triggers, so a following reload raced it. Fixing the last of these is what exposed the `-` bug above — adding the wait did not make the scenario pass, which proved the failure was in the product rather than the test.
- **A grade and penalty matrix**, in `tests/penalty_matrix_test.php`: twenty tests across assignments, forums and quizzes, covering a plain grade, a manual penalty, a late penalty, both together, penalties applied before and after grading, repeated syncs, removal, and the gradebook override lifecycle. Two of them pin the *route* rather than the arithmetic — writing `grade_grades` directly instead of going through the module API would skip the late-penalty hook and silently drop every late penalty on the course.
- Scenarios written against step definitions that were never implemented are tagged `@local_unifiedgrader_wip` and excluded in CI; the remaining 17 run for real on every build.

## v2.9.0 (2026080700)

Feature release. Adds support for **rating-based forums** — the second of Moodle's
two forum grading systems, which the grader previously did not handle at all —
together with three ways of reading a student's posts.

### New features

- **Rating-graded forums are now supported.** Moodle forums carry two independent grading systems: *whole forum grading* (one mark per student, stored in `forum_grades` on gradebook `itemnumber 1`) and *ratings* (a mark per **post**, stored in `{rating}`, with the gradebook value computed by aggregating every rating on every post the student wrote, on `itemnumber 0`). Only the first was implemented. A rating-only forum opened in the grader and *looked* like it worked — the teacher could type a grade, it was written to a `forum_grades` row on an `itemnumber 1` item that for such a forum has grade type *None*, and nothing ever reached the gradebook. A silent wrong answer rather than an error. The adapter now resolves one of three modes up front — `whole`, `rating`, `none` — and whole-forum grading takes precedence when a forum has both configured, so no forum that works today changes behaviour. All rating logic lives in a new `forum_rating_helper`, built only in rating mode; the existing adapter gains mode guards rather than rewrites.
- **Posts are rated where they are read.** In the *In context* and *Thread* views, each of the student's own post cards carries a rating dropdown in its footer alongside the current aggregate — so a teacher rates the post with it in front of them rather than matching a separate list against what they just finished reading. (*All posts* renders through a server-side iframe, so there the marking-panel list is the control.)
- **A Post ratings section replaces the grade box on rated forums.** The overview and the running total: one row per post, a rated-so-far counter, and the figure the gradebook will get with the aggregation method named ("Average of ratings", "Sum of ratings", …) so a bare number is never presented without saying where it came from. Each row shows **two different numbers on purpose**: the dropdown holds *your* rating, the figure beside it is the aggregate across every marker who has rated that post — a colleague marking the same forum moves the aggregate without touching your choice. Rows core will not let you rate (your own post, a post outside the forum's rating window, no capability) are disabled with the reason shown, rather than letting a teacher pick a value that then bounces. Choosing *Rate…* withdraws your rating rather than scoring zero. Both controls dispatch the same mutation and share one state field, so rating from either updates the other and the running total without a reload. Writes go through `rating_manager::add_rating()`, the only entry point that validates, records and re-syncs the gradebook.
- **Three ways to read a student's posts.** A rating is a judgement about *one post*, and a reply is frequently unintelligible without what it replied to — the flat list that serves whole-forum grading is the wrong instrument for it. A *Post view* switch above the preview offers **All posts** (the existing flat list, unchanged), **In context** (one post at a time with the discussion prompt, the post it replied to, the sibling replies to that same post, and the replies it drew, with a prev/next pager), and **Thread** (the whole discussion in reading order with the student's posts highlighted, long runs of unrelated posts folded away). Siblings earn their place: they are how a marker tells whether a contribution added something or restated a classmate. All three read from a single payload fetched with the student, so switching mode or turning a page costs no round trip. The choice is remembered per teacher, per forum; rated forums default to *In context*, everything else to *All posts*. Offered for whole-forum forums too — thread context helps there as well.
- **The preview pager and the ratings list stay in step.** Clicking a rating row moves the preview to that post; clicking a post in the context views highlights its row. Both components watch a single shared state field rather than calling each other, so the binding cannot drift.
- **Students see their ratings and an overall comment.** Each post in the student's feedback view carries a read-only rating badge, and the grade block names the aggregation method so a student rated on five separate posts can see the figure is an average rather than a mark somebody typed. Moodle has no field for a comment on an individual rating, so written feedback is per student, stored on the `itemnumber 0` grade item — the same mechanism already used for whole-forum grading, and the reason it is safe is that `grade_update()` builds its grade arrays without a `feedback` key, so `grade_item::update_raw_grade()` leaves stored feedback alone on every later rating change. That is load-bearing enough to be a test rather than a comment. The context views are marker-only: a student's feedback page shows their own posts alone.
- **Post ratings are visible where the post is read.** A rating badge is rendered into the post card header server-side, so the same markup serves the teacher's preview, the student's feedback view and the feedback PDF.

### Fixes

- **Clearing the last rating no longer leaves a stale grade in the gradebook.** Withdrawing a rating through core's path (`rating_manager::add_rating()` with `RATING_UNSET_RATING`, which is what `rate_ajax.php` and the forum UI use) deletes the rating but does not clear the grade it produced: `rating_manager::get_user_grades()` omits users who now have no ratings, and `grade_update()` early-returns on an empty array, so the previous aggregate survives the deletion of the mark that created it. Core also calls `round()` on the resulting null aggregate. This feature makes clearing a first-class action, so the clear path now deletes the rating directly and pushes an explicit null `rawgrade` when the student has no ratings left — a non-empty array carrying a null is what `grade_update()` needs to actually empty the cell.
- **A manual penalty on a scale-graded whole forum no longer subtracts percentage points from a scale index.** `sync_gradebook_penalty()` treated a negative `grade_forum` (which is a scale id, not a maximum) as "no maximum" and fell back to 100, so a deduction computed against a notional 100-point scale was applied to a value like `3` on a four-item scale. Scales are now left alone here, matching what `calculate_late_penalty()` and the client's penalty UI already did.
- **Quiz marks entered in the grader now reach the gradebook when a late penalty is in force.** Once a late-penalty rule has run, the gradebook cell is left *overridden* — deliberately, because that flag is what stops the quiz module recomputing the mark and wiping the penalty. But it equally blocks the new total after the manual questions are marked, so everything the teacher entered was silently kept out of the gradebook, with no error shown, until someone unticked the override by hand. The rule plugin already knows how to handle this: it listens for `\mod_quiz\event\question_manually_graded` and responds by clearing the override, letting the recomputed total through, and re-applying the penalty to it. The grader never raised that event — it writes the question usage directly, which is quicker than going through mod_quiz's grading report but skips the event that report raises. It is now raised once per question marked, after the gradebook sync so listeners recalculate from the updated total rather than a stale one. The grader continues to own no penalty logic of its own: clearing the override, recalculating and re-applying all stay with the plugin that set the penalty, so the two cannot drift apart. This also fixes any other observer of that event, not just penalties. Coverage in `tests/adapter/quiz_manual_grading_event_test.php` (the event is raised with a complete payload when a question is marked, and not raised for a feedback-only save, which would otherwise make listeners churn the gradebook for a save that changed no marks).
- **A quiz total now updates in the grade field as soon as it is saved.** After marking the manual questions the teacher had to navigate to another student and back before the new total appeared. The grade field is only written from the server on a *fresh* render — a guard that stops a background save overwriting something being typed — but a quiz total is computed by the question engine rather than typed (`quiz_adapter::save_grade()` ignores any value sent for it), so the server's figure is authoritative and was simply not being shown. It is now refreshed after a save for quizzes, guarded so it can only ever replace a value the teacher did not enter: never while the field is dirty, and never when the computed mark has been deliberately overridden.
- **Typing `--` in the grade field now clears a gradebook override on quizzes and BigBlueButton activities.** The deliberate-reset escape hatch is served by `reset_grade_and_submission()`, which assignments and forums implement but quizzes and BBB inherited from `base_adapter` — where it returned `true` without doing anything. The reset therefore reported success and changed nothing, and the override had to be cleared by hand in the gradebook. The base implementation now lifts a recoverable gradebook override, which is the meaningful reset for an activity whose mark is computed elsewhere: for a quiz the cell then recomputes from the attempt. It cannot disturb a normally-graded activity, since the underlying helper does nothing unless an override is actually present and unlocked. Present since the `--` shortcut was introduced, not a recent regression. Coverage in `tests/reset_override_test.php`.
- **A scale grade is no longer shown to students as a fraction and a percentage.** `feedback_data_helper::format_grade()` had no scale branch, so a scale-graded forum rendered as `3 / 4 (75%)` instead of the scale label — wrong for the new rated forums and already wrong for scale-graded whole forums. Scale values now render as their label, with no invented denominator or percentage; under *sum* and *count* aggregation the number is kept, since that is what those methods actually mean.

### Test infrastructure

- **Behat has never actually run, and the CI step was reporting success without executing a single scenario.** `tests/behat/behat_local_unifiedgrader.php` opened with the usual `defined('MOODLE_INTERNAL') || die();` guard. Behat loads every registered context class while it builds the suite list, which happens *before* Moodle's `config.php` — so `MOODLE_INTERNAL` was never defined and the guard fired every time. Because `die()` with no argument exits the whole process with status **0** and prints nothing, behat terminated mid-startup, the runner saw a clean exit, and the step went green. This is why core's own context classes carry the comment `// NOTE: no MOODLE_INTERNAL test here, this file may be required by behat before including /config.php.` in place of the guard; ours is now the same. The failure was total rather than partial: one bad context file takes down the run, so all eight of the plugin's feature files were affected, not just the one. Diagnosed by walking behat's controller chain — `--version`, `--help` and `--story-syntax` produced output while anything needing the suite list produced nothing, which located the death at context loading rather than at configuration or the browser. With the guard removed, `--definitions` goes from 0 to 2047 step definitions.
- **Four features were written against step definitions that were never implemented**, which the silent failure had been hiding. Every one of them is inside a scenario already tagged `@local_unifiedgrader_wip`: a PDF submission fixture (`annotation_toolbar_after_zoom`), an attached marking guide (`grade_override`), a seeded orphan submission row (`grade_reset`), and a group-selection UI step (`group_filter`). The CI Behat step now excludes that tag, so those stay parked and visible rather than deleted, and the remaining scenarios — `feedback_card_reedit`, `forum_rating_views`, `marking_keyboard_navigation`, `marking_panel_attempt_selector` — run for real.
- Two genuinely undefined steps outside any `wip` scenario are fixed rather than parked: `the "local_unifiedgrader/…" admin setting is "1"` never existed as a step and sat in the Background of `annotation_toolbar_after_zoom` (where it would have failed every scenario in the file) and in the new forum feature. Both now use core's `the following config values are set as admin:`.
- New step `the post ratings list has loaded`. The existing `the marking panel has loaded` waits for the grade input, which on a rated forum exists but is hidden and is therefore present long before the ratings arrive; a rendered rating row is the real boundary.

### Layout notes

- **The Post ratings section is a sibling of the grade section, not a child.** Rating mode hides `grade-section` to remove the grade input; nesting the ratings list inside it meant the branch that was supposed to reveal the ratings UI was the same one that hid it, so the markup rendered on every page but was never visible. Worth recording because the obvious verification — asserting the region appears in the rendered HTML — passes in exactly that broken state. Presence in the DOM is not reachability, and the check now walks the parsed DOM to assert the section is not a descendant of anything the rating-mode branch hides.

### Notes

- **Penalties and extensions are deliberately hidden on rated forums.** The gradebook value belongs to core and is recomputed from the ratings on every change, so a deduction would either be overwritten by the next rating or stick as a gradebook override that quietly stops matching the ratings it claims to represent. This mirrors the treatment scale-graded forums already receive.
- **Advanced grading is not offered on rated forums** — core supports rubrics and marking guides on the whole-forum item only (`mod_forum\grades\gradeitems::get_advancedgrading_itemnames()` returns `['forum']`).
- **A student counts as graded only once every post they wrote has been rated**, so a half-marked student stays under *Needs grading* rather than needing a new status to describe them.
- **A deliberate reset withdraws only the current marker's ratings.** Another marker's ratings are their judgement to withdraw, and a student's posts are never the teacher's to delete.
- New web services `local_unifiedgrader_get_post_ratings`, `local_unifiedgrader_save_post_rating` and `local_unifiedgrader_get_post_context`. No new database tables.
- Coverage: `tests/adapter/forum_rating_helper_test.php` (13 tests — mode resolution across all four grading-setting combinations, grade-item targeting, rate/clear round trip, average and clamped-sum aggregation, the feedback-survives-a-rating-change guarantee, no-`forum_grades`-write, the own-post and rating-window refusals, partial-rating status, and marker-scoped reset) and `tests/adapter/forum_context_builder_test.php` (8 tests — reading order and depth, metadata scoped to the graded student, two posts in one discussion yielding one prompt, discussion scoping, student-authored prompts, separate-groups visibility, empty payloads, and the whole-forum path).
- The 42 new interface strings are English-only. The plugin's other twelve locales already carry 361 of 600 strings and fall back to English for the remainder; adding machine-guessed translations for terms of art in twelve languages would be worse than the fallback.

## v2.8.1 (2026080600)
- **Fix a penalty inflating the grade instead of reducing it.** On an assignment with a penalty, the mark in the grade field could come back *larger* than the one the teacher typed — a 6/12 with a 100% plagiarism penalty redisplayed as **18/12 (150%)**, and grew again on each save. Assignments stored the *post-penalty* grade, and the marking panel reconstructed the typed mark by adding the deduction back. That round trip is only sound while the stored grade was saved under the very same penalties it is being un-deducted against, which fails in two ordinary situations: a penalty applied **after** the work was marked (the normal plagiarism workflow — the stored mark was never reduced, so adding the deduction inflated it), and a penalty large enough to clamp the stored grade to zero (`max(0, 6 - 12)`), which destroyed the original outright. Assignments now store the **raw mark the teacher typed** and apply the deduction only on the way to the gradebook — the model the forum adapter already used — so no reconstruction is needed: the field shows exactly what was entered and the gradebook carries the penalised result. New `assign_adapter::sync_gradebook_penalty()` (with a no-op default on `base_adapter`, leaving other activity types untouched); `save_grade` no longer pre-deducts for assignments and syncs the gradebook afterwards. Moodle's own late-penalty framework still applies on top, so a late submission with a plagiarism penalty gets both. **Existing grades are not rewritten:** a mark saved earlier under a penalty was stored already-reduced and will now display at that reduced value — re-saving that student restores the intended mark. Regression coverage in `tests/penalty_roundtrip_test.php` spans the reported case, the 100% clamp, repeated saves (the drift that made the bug visible), accumulating and cleared penalties, the end-to-end path through the `save_grade` web service, and a guard that forum behaviour is unchanged.

## v2.8.0 (2026080100)

Feature release. Adds a **dual file view** so two of a submission's files can be
marked side by side — built for the case where a student submits a recording and
its manuscript together, and the grader needs both on screen at once.

### New features
- **Dual file view (two submissions at once).** A new toggle in the layout controls splits the preview into two stacked panes with a draggable divider, so a teacher can watch a recorded speech while marking its manuscript. Stacked rather than side by side deliberately: each pane keeps the full pane width, so the comment margin is not squeezed out of the document. The divider drags to trade height between the panes (double-click resets, arrow keys nudge it when focused), letting the video be shrunk to give the manuscript as much room as possible. Each pane has its **own file chooser**, which is how submissions with more than two attachments are handled — any two sources can be paired, rather than being fixed to the first and second. The panes seed themselves for the intended case: a recording on top, the annotatable document below. The toggle only appears when there are at least two previewable sources, and is an independent on/off that composes with the existing Split / Preview-only / Grading-only layouts rather than replacing one of them.
- **Marking follows the focused pane.** Both panes can hold real, clickable documents, so exactly one is active at a time — shown by a "Marking here" badge and a ring around the pane. Clicks and text selections in the other pane cannot place a mark, so a stray click while scrolling for reference can never drop a comment into the wrong document. The same guard applies to the Fabric tools (pen, shapes): tool events are dispatched on `document`, so without it selecting the pen would have armed it in *both* panes at once.
- **A recording embedded in online text works as a pane source.** A clip recorded with the TinyMCE recorder lives inside the submission's online text, not in a file, so submission content is offered as a pane source in its own right. The text renders inline in the pane, so the recording plays and the words stay annotatable. Embedded media (`.satsrecorder-media-wrap`, or a bare `<video>`) is sized to the pane and rescales as the divider moves, instead of keeping its intrinsic size and being clipped.
- **File type icons on the submission tabs.** Each file pill now carries an icon for its kind — video, audio, Word, PDF, spreadsheet, presentation, or a generic document — so with several attachments the teacher scans for the *kind* of file rather than reading filenames. Falls back to the file extension when a source reports a generic mimetype.
- **Free-floating tick and cross stamps.** The shape dropdown gains a tick and a cross that are placed at a click rather than bound to text. The text-anchored marks cover commenting on wording (and carry through the translation pipeline), but a cover page, diagram or signature block has no text to anchor to — these fill that gap. They are canvas objects, so they move, undo and flatten into the downloadable PDF like the other drawn annotations.

### Fixes
- **Stop a plagiarism plugin's JavaScript being printed into the student's feedback PDF.** The plagiarism section reduces the plugin's HTML to text with `strip_tags()`, which removes the tags but keeps the text *between* them — so an inline helper shipped alongside the scores (Copyleaks' copy-to-clipboard function) was typeset verbatim into the student's feedback, immediately after the similarity scores. `pdf_text::plain()` now drops `<script>`/`<style>` blocks together with their contents, including an unclosed `<script>`, which would otherwise have leaked everything following it. The same gap is closed in the overall-feedback path (`sanitise_feedback_html()` stripped media and inline event handlers but not script blocks). The real scores are unaffected. Regression coverage in `tests/pdf/pdf_text_test.php`.

## v2.7.2 (2026073100)
- **Fix a late penalty being deducted twice when a grade is recalculated.** Granting an extension (or otherwise triggering a recalculation) on a late assignment took the penalty off the grade *twice* — a 7-days-late submission under a 5%/day rule lost 70% instead of 35%. `recalculate_penalty.php` and `extension.php` both called `assign_update_grades()` and then `\mod_assign\penalty\helper::apply_penalty_to_user()`, but the first already applies the penalty: it runs `assign_grade_item_update()`, which ends by calling `apply_penalty_to_user()` for each affected user. The doubling is exact rather than compounding because `gradepenalty_duedate` deducts a **fixed** number of marks (max grade × penalty%, not a share of the remaining grade), and core has no "already penalised" guard — `is_penalty_enabled_for_grade()` only rejects minimum, overridden and locked grades. The redundant second call is removed from both entry points; the standalone `apply_penalty_to_user()` calls elsewhere (`overrides_extensions.php`, `clear_all_overrides.php`) are single applications and are unchanged. Present since 2026-04-08 and only reachable through the extension/override recalculation path, which is why routine grading never showed it. Grades already recorded under the doubled penalty are not retroactively corrected — re-saving an affected student's grade recalculates it correctly. Regression coverage in `tests/penalty_double_apply_test.php` fails the build if any plugin file re-applies the penalty after a full recalculation.
- **Reword the tick/cross annotation tooltips so each reads correctly on its own.** The cross was labelled "Correct (cross)", which only parses if you take *correct* as a verb — on a ✗ it can just as easily be read as "this is correct", the opposite of what the mark means. The tick's "Affirm (tick)" was carrying all the disambiguating context, so the pair only made sense once you had seen both. They are now written as a matched pair describing what the mark tells the student: **"Good point (tick)"** and **"Needs correction (cross)"**. The obvious alternative — *Correct* / *Incorrect* — was rejected because it would move the word "correct" from the cross to the tick, so anyone who had learned the old label would read the same word as meaning the opposite. Only the English strings define these (every other locale falls back), so no translations were invalidated.

## v2.7.1 (2026073000)
- Fix a student's feedback view silently dropping the grader's annotations when the displayed attempt isn't the student's absolute-latest one — e.g. after a resubmission that was itself also graded, `view_feedback.php` shows the latest *graded* attempt (which can be an earlier one), but `get_student_annotations` validated the requested file only against `get_submission_files()`, which always resolves the latest attempt regardless of grading state. When the two diverged, the file-ownership check silently failed and the endpoint returned an empty array — no error, the annotations just never appeared, even when the student explicitly selected the correct attempt via the attempt dropdown. `get_student_annotations` now takes the attempt the feedback view is actually displaying and validates against that specific attempt's files (`get_submission_files_for_attempt`), falling back to latest-attempt behaviour when no attempt is supplied. Wired through `feedback_viewer.js` → `annotation/persistence.js`, using the `data-attempt` value the template already exposed. PHPUnit regression coverage in `tests/external/annotation_webservices_test.php` (`test_get_student_annotations_respects_selected_attempt`).
- Fix the marking panel's attempt selector staying hidden for a teacher even when a student genuinely has more than one submission attempt. `_renderAttemptSelector` hid the selector whenever the activity's `maxattempts` was `1`, on the assumption that `maxattempts === 1` means there will only ever be one attempt — but `maxattempts` only caps a *student's* automatic reopens; a teacher can still manually reopen a submission (`attemptreopenmethod: manual`) regardless of that cap, producing a real second attempt the selector then had no way to surface. The teacher had no way to see or switch back to an earlier, already-graded attempt in that case. The student-facing feedback view never had this bug — it always based visibility purely on the actual attempt count — which is what made the teacher-side gap easy to miss. The check is now `attemptList.length <= 1`, matching the student view's logic; `maxattempts` is no longer consulted for visibility. No JS unit-test infrastructure exists in this project for the marking panel (Behat is the normal coverage path for reactive-UI behaviour); Behat scenario coverage in `tests/behat/marking_panel_attempt_selector.feature`, including a negative case confirming the selector still stays hidden for a genuine single-attempt submission.

## v2.7.0 (2026072300)

Major release. Consolidates the two large feature streams built since v2.6.6 —
grader-facing **submission translation** (via `local_nida`) and a **PDF / online-text
annotation** overhaul — which shipped incrementally as the 2.6.7–2.6.18 dev builds
but were never captured here, plus this cycle's BigBlueButton recording-selection
fixes and translation hardening. Feature summaries below are consolidated from the
intervening commits; the two fixes at the end are described in full.

### New features (consolidated from 2.6.7–2.6.18)
- **Submission translation for graders (local_nida integration).** When `local_nida` is installed and enabled for a course, the document-preview pane can show an English machine translation of a non-English submission alongside the original, with a machine-translation advisory, a mixed-language warning, and a side-by-side ("parallel") sub-mode. A submission-language badge lets the grader confirm/override the detected language so feedback is translated back into the student's language. Degrades cleanly when `local_nida` is absent or a course isn't enabled (see the hardening note below). New external functions `get_submission_translation` and `confirm_student_language`.

### Security
- **CRITICAL — Fix stored XSS in submission comments.** `local_unifiedgrader_scomm.content` was stored raw via `add_submission_comment` (`PARAM_RAW`), returned raw by `get_submission_comments` (`PARAM_RAW`), and assigned to `innerHTML` in four JS files (the marking-panel chat widget, the on-activity chat bubble for quiz/forum/BBB, the inline assignment widget, and the student feedback view). The "Trust boundary" comments in the four JS files used to claim the content was sanitized by Moodle core's comment API — that was false (the plugin uses its own `submission_comment_manager` table, not the core comment API). The comments have been corrected to describe the real trust boundary.

### Performance
- **HIGH — Batch the N+1 participant query in assign.** `assign_adapter::get_participants()` used to fire `get_user_submission()` + `get_user_grade()` + `get_user_flags()` once per participant — three DB round-trips × N students on top of the user_picture rendering. For a 500-student course that was ~1500 single-row queries; for 5000 students, ~15000. The forum, quiz, and bbb adapters were already batching these correctly; only the primary use case was slow. `get_participants()` now batch-loads all three tables once outside the loop using `get_records_sql` with a `MAX(attemptnumber)` self-join for the latest-attempt semantic on submissions and grades, plus a single `get_records` for `assign_user_flags`. Drops 3N round-trips to 3 fixed queries. Team-submission assignments (a small minority where submissions are keyed on `groupid` rather than `userid`) fall back to the original per-user path — the batching doesn't apply to that shape.
- **MEDIUM — Batch tag + proposal lookup in the comment library.** `comment_library_manager::format_comment()` was doing 1–2 DB queries per comment (a tag-id fetch via `get_fieldset_select`, plus optionally a per-comment proposal-status lookup). A teacher with 200 personal comments paid 200–400 queries every time the comment-library pill rendered — which is on every page load and after every save. A new `prefetch_comment_metadata()` helper batch-loads `local_unifiedgrader_clmap` and `local_unifiedgrader_clibprop` via `get_in_or_equal()`, builds two id-keyed lookup maps, and passes them into `format_comment()` (now a pure array transform — no DB). Brings the per-render cost to 2 fixed queries regardless of comment count. All three internal callers (`get_comments`, `get_system_comments`, `get_shared_comments`) updated to call the prefetch once before the format-loop.
- **MEDIUM — Batch author lookup in `notes_manager::get_notes()`.** The render loop did `\core_user::get_user($note->authorid)` per note — static-cached after the first hit but cold renders still paid per author. Now a single `get_records_select('user', "id $insql", …)` upfront, using `\core_user\fields::for_name()->with_userpic()->get_required_fields()` to pick up the full set of fields needed for `fullname()` and user-picture rendering.

### Concurrency / data integrity
- **MEDIUM — Fix annotation save race with UNIQUE constraint + transaction.** `annotation_manager::save_annotations()` did `get_record` → conditional `insert` / `update` / `delete` per page with no transaction and no unique constraint on `(cmid, userid, authorid, fileid, pagenum)`. A fast-typing teacher (the annotation layer autosaves on every tool action) could fire two overlapping WS saves; both observe "no row exists" via `get_record`, both insert, producing duplicate rows that then corrupt subsequent reads. The composite index `ix_cmid_userid_fileid` was non-unique so the schema did nothing to prevent this. Replaced by a strictly-superset UNIQUE index `uix_cmid_userid_authorid_fileid_pagenum` (still index-accelerates the `cmid + userid` partial-prefix reads). An upgrade step (gated at savepoint `2026052900`) de-duplicates any existing colliding rows before adding the unique index — the de-dup keeps the row with the highest `id` per composite key, since `annotationdata` is overwritten on subsequent saves anyway. The save batch in `save_annotations()` is now wrapped in `\core\dml\moodle_database::start_delegated_transaction()`; the race loser hits the unique constraint, the transaction rolls back cleanly, and the client can retry instead of leaving half-applied state.

## v2.4.7 (2026-05-26)
- Release the PHP session lock in all 41 web service handlers immediately after capability checks. **Background:** Moodle (and PHP itself) holds a per-user session lock for the entire lifetime of every request — the lock exists to prevent two concurrent requests from the same user from racing to write `$SESSION`. While the lock is held, every other AJAX call from the same teacher serialises behind the running one, even if the requests are completely independent. The Unified Grader fans out a lot of parallel WS calls in normal use — picking a student fires `get_submission_data` + `get_grade_data` + `get_participants` + `get_annotations` + `get_notes` + `get_submission_comments` + `prepare_feedback_draft` + `prepare_feedback_files_draft` simultaneously; debounced autosave fires `save_grade` mid-edit; the annotation layer pings `save_annotations`. With the session lock held by an in-flight `save_grade` (which itself runs Moodle core's heavy grade-pipeline + file moves), the next eight requests queue up. If `save_grade` takes long enough — slow gradebook recompute, big course, contended DB — the queued requests trip Moodle's `session_lock_expire` of 2 minutes and the teacher sees: *"Unable to obtain lock for session id session_XX within 2 mins. It is likely that another page (.../save_grade) is still running in another browser tab."* **Fix:** none of our 41 WS handlers writes to `$SESSION` after authentication, so each one now calls `\core\session\manager::write_close()` immediately after `validate_context()` + `require_capability()`. The session is closed, the lock is released, and concurrent requests proceed in parallel instead of head-of-line-blocking behind a slow save. For the three handlers where capability is conditional (grader-or-student paths in `add_submission_comment`, `get_submission_comments`, `delete_submission_comment`), the close was moved out of the defensive throw-only branch so it always runs after every auth gate has passed.
- Slow-save instrumentation: `local_unifiedgrader_save_grade` now emits a `debugging()` warning when a single grade save exceeds five seconds, with cmid, userid, elapsed time, and the most likely culprit dimensions (adapter type, whether advanced grading was in play, feedback draft sizes). Five seconds is well below the 2-minute session-lock timeout but well above normal save latency, so admins running with developer debug get early warning of a real bottleneck (gradebook recompute on a heavy course, DB contention, a misbehaving event observer) without daily noise. No effect on normal operation.
- Profile popout now offers a "Send mail" shortcut into `local_satsmail` when that companion plugin is installed. Previously the email line below the student's name was a plain `mailto:` link that opened the teacher's external mail client — useful, but it bypassed the satsmail audit trail and lost the course context. When satsmail is detected (presence check on its compose entry point, not a class autoload so it degrades cleanly when satsmail isn't deployed), the email line becomes a "Send mail" link that opens satsmail's compose flow with the course and recipient pre-filled. The student's email address remains visible on hover (and in the full profile view). When satsmail isn't installed the popout falls back to the existing `mailto:` behaviour.
- Fix the participants list showing "Graded" for a submission that has just been reverted to draft from the marking panel. `assign_adapter::resolve_status()` was returning `'graded'` whenever an `assign_grades` row existed, regardless of the underlying `assign_submission.status`. Reverting to draft flips the submission row to `draft` but deliberately leaves the grade row intact (so the teacher's previous mark is preserved for next time) — the participant pill then kept saying "Graded" while the marking-panel pill, which reads `submission.status` raw, correctly said "Draft". Two contradictory verdicts for the same student. The resolver now treats an explicit `draft` or `reopened` status as authoritative and only falls through to the grade-row check when the submission is still in a graded-or-submitted shape. Regression test in `tests/adapter/assign_adapter_test.php` (`test_get_participants_reverted_graded_submission_shows_draft`) pins the behaviour.

### Auto-save race fixes (affect all activity types, not just BBB)
- `_renderGuide` and `_renderRubric` switch from destructive `innerHTML = ''` rebuilds to incremental DOM updates: snapshot values at save dispatch, then on the post-save state refresh keep the focused field — and any field edited since the save fired — instead of clobbering it
- Same protection extended to the top-level grade input, scale dropdown, and TinyMCE feedback editor (`setContent()` calls during a state refresh now refuse when the editor has focus or contains unsent edits)
- Re-mark grade dirty after a reconciled refresh so the next focusout flushes a follow-up save
- Treat `focusout` with null `relatedTarget` as ambiguous (defer to a microtask and re-check `document.activeElement`) — fixes marking-guide values resetting when opening the comment library in WebKit/Safari
